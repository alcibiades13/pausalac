# Decisions log

Running log of engineering conventions decided per the master prompt's §81 rule: if a choice doesn't touch money, legal compliance, tax treatment, security, or irreversible data, decide it, document it here, and move on rather than blocking on it. Reference `docs/implementation-plan.md` for the full architecture rationale — this file is just the append-only decision record.

Add new entries at the bottom, in the same table row format, as Phase 1b+ raises new ones (auth session strategy, ERD specifics, permission matrix, etc.).

| 2026-09-13 | DRF defaults: session auth (placeholder — real auth strategy is a Phase 1b decision), `IsAuthenticated` by default, page-number pagination, `django-filter` + search/ordering backends, URL path versioning (`v1`). | Reasonable DRF starting defaults; none of this is a business-logic commitment, all overridable per-view. |

| 2026-09-13 | `/health` endpoint added directly in `config/` (not a domain app) — deliberately dependency-free for now (process liveness only, no DB/broker checks). | Master prompt §68 requires a health endpoint from the start; a real readiness check (verifying Postgres/Redis/storage) is deferred until those integrations exist to check. |
| 2026-09-13 | Requirements split into `requirements/{base,dev,production}.txt` rather than a single `requirements.txt` or Poetry/PDM. | Keeps dev-only tooling (pytest, ruff, factory-boy) and prod-only tooling (gunicorn) out of each other's install; no need for a lockfile-based Python tool yet at this scale. |
| 2026-09-13 | Phase 1b auth strategy: Django session cookies + CSRF (DRF `SessionAuthentication`), confirmed with user over JWT. `apps/app` and `apps/api` share credentials via cookie; SPA primes `GET /api/v1/auth/csrf/` and echoes the cookie back as `X-CSRFToken` on mutating requests. | Matches master prompt §49's "session management" language; keeps the session token out of JS-reachable storage (lower XSS blast radius) versus a bearer JWT in localStorage. Trade-off accepted: production needs `apps/app`/`apps/api` on a shared parent domain (`SESSION_COOKIE_DOMAIN`) — tracked as a deploy-time TODO in `config/settings/{staging,production}.py`. |
| 2026-09-13 | Custom `User` model (`apps.accounts`), email as `USERNAME_FIELD`, no username field. Set as `AUTH_USER_MODEL` before any other migration existed. | Standard Django best practice — swapping the user model after the fact requires a painful migration; doing it first avoids that entirely. |
| 2026-09-13 | Tenant resolution implemented as DRF permission classes (`apps.companies.permissions.resolve_company`, `HasActiveCompany`, `HasCompanyPermission(codename)`) that set `request.company` as a side effect of `check_permissions`, rather than a middleware or an `APIView.initial()` override (both considered in the Phase 1b plan). | `initial()` runs permission checks internally; overriding it to set `request.company` *before* `check_permissions` would mean re-implementing DRF's internal dispatch order by hand — fragile across DRF versions. Setting it inside a permission class's `has_permission()` is simpler, well-established, and DRF already guarantees permissions run after authentication and before the view body. |
| 2026-09-13 | Two distinct tenant-addressing patterns coexist on purpose: `Company` itself is addressed by its own `pk` in the URL (`/companies/{id}/`, permission-checked via `IsCompanyMember`/`IsCompanyOwner` object permissions) because a user may hold memberships in several companies before "picking one"; everything *under* an active company (audit log now, invoices/clients/etc. later) is addressed via the `X-Company-Id` header (`resolve_company`). | Company is the thing you choose between; everything else assumes you've already chosen. Conflating the two would mean either double-specifying the company (URL + header) for domain resources, or losing the "which of my companies am I looking at" list/switch UX for Company itself. |
| 2026-09-13 | Cross-tenant object access returns 404 (via a pre-scoped `get_queryset()`), not 403, for `Company` detail; anonymous requests against `IsAuthenticated`-only endpoints return 403, not 401 (DRF's own behavior — `SessionAuthentication` provides no `WWW-Authenticate` challenge, so DRF downgrades `NotAuthenticated`/`AuthenticationFailed` to 403). | Both are deliberate: 404 avoids confirming a tenant-scoped row exists at all to a non-member; the 401→403 downgrade is un-overridden default DRF behavior, documented here so it isn't mistaken for a bug later. Covered by tests in `apps/companies/tests/test_views.py` and `apps/accounts/tests/test_views.py`. |
| 2026-09-13 | RBAC permissions are data (`apps.accounts.permissions.ROLE_PERMISSIONS: dict[role, set[codename]]`), not per-view if/else. `Membership.Role` already includes `ACCOUNTANT`/`ACCOUNTANT_ADMIN` (unused until Phase 4) so that phase needs no migration reshuffle. Exact accountant-role permission split is a placeholder, narrow it when Phase 4 clarifies real needs. | Mirrors the rules-engine philosophy (§25) applied to RBAC — one dict is the only place permission grants should ever need to change. |
| 2026-09-13 | API error contract (`config/exceptions.py`) prefers a Serbian fallback message when an exception carries DRF's own unmodified default detail (e.g. bare `NotAuthenticated()`); app-raised messages (already Serbian) and serializer field-validation errors are passed through as-is. | Full localization of every DRF/serializer built-in validation message is deferred — the stable `code` in the error contract is what the frontend should key its own localized copy off of for anything more specific than the common default-detail cases this covers. |
| 2026-09-13 | `packages/ui` ships no build step — raw `.vue`/`.ts` consumed directly via the pnpm workspace symlink, `vue` as a `peerDependency`. `apps/app/vite.config.ts` reads the repo-root `.env` (`envDir`) instead of a separate `apps/app/.env`. | One Vue instance in the tree; one env file shared with the backend instead of two to keep in sync. |
| 2026-09-13 | **Bug found via the Phase 1a build-verification habit, fixed immediately**: Tailwind v4's automatic content detection does not scan `packages/ui` — it walks each app's own directory and skips `node_modules`, and `@pausalac/ui` is resolved from `apps/app/node_modules/@pausalac/ui` (a pnpm symlink) even though the real files live outside `node_modules`. Utility classes used only inside shared components (e.g. `Alert`'s `bg-danger/10`) were silently absent from the built CSS. Fixed with an explicit `@source "../../../../packages/ui/src";` in `apps/app/src/assets/main.css` (Tailwind v4's documented escape hatch for exactly this monorepo case). Confirmed by grepping the built CSS for those classes before and after. | Add the same `@source` line to `apps/web/app/assets/main.css` the day it first imports a `@pausalac/ui` component — it doesn't need it yet (no such import exists there today) but will hit the identical silent gap otherwise. |
| 2026-09-13 | No HTTP client library (native `fetch` wrapper, `apps/app/src/lib/api.ts`), no form-validation library, no global Toast system yet. | Four simple auth forms don't justify the dependencies; revisit when invoice forms (Phase 2) or the notifications domain (Phase 3) actually need them. |
| 2026-09-13 | API error contract extended with an optional `fields` key (`{"error": {code, message, request_id, fields?}}`) — found necessary while wiring RegisterView's inline field errors: the original Phase 1b contract flattened all serializer validation errors into one `message`, losing which field(s) failed (violates §93's "inline errors"). `config/exceptions.py::_extract_fields` populates it for dict-shaped validation errors only. | A phase-2-reveals-a-phase-1b-gap fix — documented here rather than worked around awkwardly in the frontend, with regression tests added in `apps/api/config/tests/test_exceptions.py`. |
| 2026-09-13 | `apps.clients` is the first business-domain model to use `TenantScopedManager` (apps/companies/managers.py) as its *default* `objects` manager (not a secondary one, unlike `Membership.by_company` in Phase 1b). Tenant-scoped via the same `X-Company-Id` header mechanism the audit endpoint already used, now proven on a writable resource with full RBAC (`view_clients`/`manage_clients`) and soft-delete (`perform_destroy` sets `is_active=False`, never a hard delete). | Validates the Phase 1b pattern end-to-end before Invoices/Payments (Phase 2b+) build on the same manager and header mechanism at larger scale. |

| 2026-09-13 | Frontend: `currentCompany`/`currentCompanyId` (`src/stores/company.ts`) auto-selects the caller's first active membership; the persisted `localStorage` id is only a convenience, always re-validated against `auth.user.memberships`. | 2026-09-13 | **⚠️ Invoice numbering format not verified against authoritative Serbian requirements** — implemented as per-company, per-calendar-year sequential (`INV-{year}-{seq:03d}`, resets each year), assigned only at issue time (drafts stay unnumbered). Matches the master prompt's own illustrative examples (§13, §21) literally, but continuity rules, whether an annual reset is permitted, and whether "INV" is an appropriate prefix for a Serbian-market document have **not** been confirmed against an authoritative source. | Same category as the illustrative 6M/8M RSD limit figures flagged in Phase 0 — confirm with an accountant before any real invoice goes out. `apps.invoices.numbering.assign_invoice_number` is the single place to change if the format needs to differ. |
| 2026-09-13 | `FinancialEvent` (master prompt §21) lives in `apps.invoices`, not a new dedicated app — the domain list (§44) has no ledger app, invoices is the sole producer until Payments (2d) joins it. | 2026-09-13 | Invoice numbering assigned only at **issue** time, not creation — drafts stay unnumbered (`invoice_number=NULL`) so abandoned drafts don't burn sequence numbers. | 2026-09-13 | Editing an invoice is DRAFT-only; `ISSUED`/`CANCELLED` have no PATCH path at all, only the explicit `issue`/`cancel` actions (`InvoiceService`).
